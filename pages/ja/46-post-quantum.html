耐量子化への移行

2026-09-12 時点では、署名・鍵交換のハイブリッド実装と、commitment・証明・決済状態まで対象にする PQC 研究を区別する。新規ネットワーク上で限定した証明と状態更新を実行したが、実用 note と市場全体の PQC 化は未完成である。既存台帳の移行は対象にせず、既存環境を保持する。

証明・新規ネットワークの実装記録 · PQC note の実装範囲 · 2026-09-12

加法準同型の代わりに、秘密の計算関係を証明する

PQC note の方針は、秘密の数量と乱数を SHA-512 で commitment にし、その開封関係と決済の計算を証明することである。ハッシュ自体に加法準同型性はない。説明用に C0 = H(v0 || r0)、C1 = H(v1 || r1)、C2 = H(v2 || r2) と書けば、秘密の入力についてこれらの等式、v0 = v1 + v2、数量の範囲を同時に証明する。実際の形式はドメイン、配備方針、資産、所有権も結び付ける。

DeFMI は公開 commitment と証明を受け取り、正規台帳の入力、支出権限、nullifier の未使用、出力との関係を検証して状態を更新する設計である。単に開封をサーバーへ渡してハッシュを照合する処理では秘匿証明にならない。ハイブリッド署名を付けるだけでも、Pedersen の束縛や note 証明の耐量子化にはならない。

実行済みの研究と未完成の実用経路

  • 実行済み:ハッシュ・符号・sumcheck に基づく協調証明。7 者の所有者別入力で限定した 4 口座の算術関係を証明し、独立した公開データだけの検証器で確認。暗号化入力の実験では、約定・非約定と復旧を含む 740 の正規 Block/State 遷移を記録した。別の新規ネットワーク実験では、1 ホスト上の 5 検証者で受理と再起動後の状態一致を観測した。
  • 実装途中:新しい PQC note の形式、受取人だけが持つ支出鍵、ハイブリッド暗号化による配送とウォレット内の復号。完全な note の秘密計算関係、特に出力暗号化の証明、匿名の所属・支出、予約・約定・返却を結び付ける実用経路は未完成である。
  • 判定:実行した研究は smoke_only。独立運営者による保管、実際の QOMM/OCLOB 入力からの全経路、構成全体のゼロ知識性・量子攻撃に対する健全性・具体的安全性パラメータの外部検証は残っている。

基盤: zkfmi-crypto

他のすべてのリポジトリが、git rev を固定して依存する crate が一つある。この crate は語彙（スイート名や鍵の種類）と、それらの組み合わせ方を定める。各サービス自身の鍵保管や、DeKYX の発行者 epoch（鍵の世代）を置き換えるものではない。それらに共通の形を与える。

  • スイート識別子。一覧は閉じていて、版が付く。使用中の古典スイート（Ed25519、ristretto255 上の FROST、ristretto255 上の Pedersen と Bulletproofs、TLS 1.3 の X25519、SHA-256/512、SHAKE128）、耐量子スイート（ML-KEM-768、ML-DSA-65、ML-DSA-44、SLH-DSA-SHA2-128s）、ハイブリッド（X25519MLKEM768、Ed25519+ML-DSA-65）を含む。各スイートは用途とバイト長を持ち、テストで FIPS 203/204/205 の定数と照合する。未知のスイートや版は拒否する。既定値に読み替えることはない。
  • 正規化した署名入力。署名の対象となるバイト列の並べ方を一つに決めたもの。プロトコル、版、ネットワーク、配置、契約、トランザクション種別、オブジェクト識別子、シーケンスまたは nonce、期限、スイート、本文ハッシュを、それぞれ固定幅整数の長さ接頭辞を付けて、ドメイン ZKFMI:CANONICAL:v1 の下に並べる。期待値となるバイト列（golden ベクタ）は hex で固定してある。同じ本文でも用途が違えば署名の入力が変わる。したがって、ある用途の署名を別の用途に流用できない。
  • 用途に束縛した鍵。鍵レコードには、参加者、用途（見積、決済指図、鍵の交代、統治、トランスポート、attestation）、スイート、世代、有効期間、失効、交代の証明を書く。鍵の交代は双方向に署名する。旧鍵が新鍵に署名し、新鍵が旧鍵の識別子に署名する。
  • ハイブリッド署名。同じ正規化入力に対して、Ed25519 と ML-DSA-65 の両方で署名する。検証は両方が通ったときだけ受理する。片方が失敗、片方が欠落、二つが入れ替わっている、のいずれも拒否する。ML-DSA のコンテキスト文字列には用途とスイートを入れる。
  • ハイブリッド鍵交換。X25519 と ML-KEM-768（KEM、鍵カプセル化: 公開鍵で共有秘密を包んで送る仕組み）を、それぞれ独立に生成した秘密で動かす。両方の共有秘密、両方の暗号文、スイート識別子を HKDF-SHA256 に通して一つの鍵にまとめる。どちらの半分を差し替えても導出される鍵が変わることを、テストで確かめている。
  • バックエンド。RustCrypto の ml-dsa 0.1.1 と ml-kem 0.3.2（純 Rust、Apache-2.0 OR MIT）を使う。バイト指向のトレイトの背後に置いてあるので、aws-lc-rs のような FIPS 認証済みのバックエンドに後から差し替えられる。古典側は ed25519-dalek 2.2 と x25519-dalek 2.0。#![forbid(unsafe_code)] を指定し、秘密はメモリから消去（zeroize）する。この選択は工学上の選択であり、本番・監査・FIPS の主張ではない。

増えた時間の内訳。注文ごとに 7 つの MP-SPDZ プロセスを起動し直し、各プロセスは相互認証つきの TLS 接続を 12 本張るので、1 回で 42 回のハンドシェイクが起きる。同じ OpenSSL 3.5.5 でループバック上のハンドシェイク 1 回を測ると、従来版が使っていた RSA-2048 証明書で 1.07 ms、Ed25519 証明書で 0.56 ms、ML-DSA-65 証明書と X25519MLKEM768 で 2.19 ms だった。OpenSSL 3.5.5 の ML-DSA-65 署名は 1 回 0.69 ms で、これが最も大きい項であり、1 回あたりおよそ +13 ms になる。ハイブリッド版はさらに、45 MB のエンジンのバイナリを毎回読み直して .pqc-tls.sha256 の受領証と照合しており、これに約 35 ms かかる。この検査は移行で加えたもので、MPC の計時が始まる前に動く。ハイブリッドのアプリ署名（計画 1 件、参加者の受領証 7 件、ノードの受領証 1 件、遷移の証明 5 件、3 ノードの定足数）は見積もりで 10〜20 ms を足す。残る 30〜40 ms は暗号以外のビルド差で、今回は分けていない。

計画の目標に対して。この経路の処理量は従来の 95.5% と 95.9% で、目標の 95% を半ポイント上回る。追加の遅延は p95 で 16 ms と 76 ms で、目標の 5 ms を満たしていない。実行前に書いた予測は差を −10〜+5 ms と見ていて、二つの点で外れた。エンジン受領証の検査を起動時の 1 回だけと思っていたこと、ML-DSA-65 の署名が RSA-2048 の署名より速いと見ていたことである。OpenSSL 3.5.5 では 0.69 ms 対 0.27 ms で逆になる。この二つは同じ日のうちに直した。エンジンのバイナリはプロセスごとに 1 回だけハッシュし、回ごとにはファイルの識別情報で確かめる。デモの実行器は 7 つのプロセスを回をまたいで維持し、各回の入力を名前付きパイプで渡す（ネイティブ受入の 7 プロセス構成は今も回ごとに起動する）。表の 2 回目の行がその結果で、ハイブリッド画像は従来版より注文 1 件あたり 177 ms と 202 ms 速くなり、計画の目標は二つとも、公開していた従来版に対して満たした。同じ実行器を載せた従来版なら、ハイブリッドのアプリ署名の分だけ、見積もりで 10〜20 ms さらに速いはずである。実行前に書いた予測はもっと大きな短縮（1 回あたり 300 ms 以上。実測は 250 と 276）を見込んでいて外れた。プロセスの起動、接続の確立、受領証のハッシュで約 250 ms、残る 500 ms は回路そのものの前処理とオンライン段階で、MP-SPDZ はこれをループの中でも回ごとに生成する。

8 リポジトリすべてのソースを一つのスナップショットに凍結した（1,119 ファイル、実行の前後でハッシュが一致）。これを Linux ホスト 1 台で固定イメージにビルドし、その上で次を動かした。ハイブリッド TLS アダプタ上の MP-SPDZ プロセス 7 つ、DeFMI の L1、OCLOB のメイカー API とテイカー API。4 つのシナリオが順に通り、合計 15 分。

  • 市場: 3 ラウンド。自律決済 2 件、耐量子の応答署名 4 本、一回限りの鍵 8 本。応答を失った後の復旧。重複決済はゼロ。
  • finality: 署名付きの秘匿状態の受領証が、同じプロセス内の再試行、再オープン後、別プロセスからのいずれでも、バイト単位で同一に返る。二重適用は拒否。7 ノードの正規化された観測。差し替えは拒否。ウォレットの再オープン。請求 3 件。秘匿保証枠の witness（証明の秘密入力）2 件を復旧し、次の注文で消費。
  • lifecycle: 約定 3 件、新しい耐量子鍵 12 本、応答署名 6 本。部分約定の後に順序付きで取消し、厳密なリプレイと再起動を含む。期限切れによる解放。7 ノードの再起動チェックポイント。
  • P6 復旧: 新たに解決した不変な依存関係の下での復旧テスト 2 件。

この実行で欠陥が 2 件見つかり、通過前に修正した。一つは、再試行ごとに ML-DSA 署名を作り直していた受領証で、署名済みの受領証を永続化して再送するようにした。もう一つは、部分約定の後に返金の開封値が新しい操作識別子で再認可されていたもので、元の請求コンテキストを保持するようにした。補助ゲートは次のとおり。OCLOB のテスト 125 件、zkPI・DeKYX・DeCCP・P5 の各ワークスペースにわたるテスト 279 件、QOMM のトランスポートとデモのテスト、Aethel のエンドツーエンド。すべて strict clippy 付き。

既存の古典経路と新規 PQC 研究の境界

既存の Pedersen・Bulletproofs・Triptych・FROST 経路は離散対数に依存し、新しい資産 ID 秘匿の Ristretto 経路も PQC On では拒否する。PQC 研究では SHA-512 と符号ベースの証明を使い、BN254 は算術の体としてだけ使う。楕円曲線 commitment、ペアリングの最終証明、委員会署名を証明の健全性の代わりに使う構成ではない。これでも、実装した構成全体の耐量子安全性が確立したことにはならない。

根拠の限界

  • ホスト 1 台、管理者 1 人。独立した運営者、WAN、物理 HSM はない。
  • バックエンドの FIPS 認証も外部監査もない。
  • 性能比較は、空いている 1 台のホストで、公開していた OCLOB の二つの画像をループバック上で 1 回測ったものである。計画の処理量の目標（基準値の ≥95%）は半ポイントの差で満たす。遅延の目標（p95 のオーバーヘッド 5 ms）は満たしていない。p95 で、板に残る注文は +16 ms、約定する注文は +76 ms である。7 プロセスのネットワーク障害テストは、7 ノードの WAN の根拠にはならない。
  • P5 の証明器は本家の alpha 版（Miden 0.32）に依存し、意図的に狭い命題を証明する。
