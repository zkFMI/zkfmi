現状と受入

「実装済み」はコードが存在し、固定した workspace でテストが通ることを意味する。「受入済み」はリポジトリのリリースゲートで、記載の構成上で動いたことを意味する。どちらも本番を意味せず、複数ノードの受入はすべて、記載の構成が 1 人の管理者の下の Linux ホスト 1 台である。

最終確認: 2026-09-07 時点のリポジトリ先頭

一段落の要約

端から端までの経路は存在し、実行済みである。参加者が注文または依頼を分割し、7 つの MPC プロセスがそれを計算し、3-of-7 の定足数が閾値 zkPI を発行し、Rust VM を動かす 5 台の AvalancheGo 検証者が両脚を原子的に決済し、状態 root で合意し、リプレイを拒み、再起動した検証者 1 台を同じ root で復旧させる。これはネイティブ実行と復旧の証拠である。独立した組織、WAN、HSM 保管鍵、監督当局の鍵儀式、法的 finality 制度の証拠ではなく、そのどれも試みていない。

ゲートが実行するもの

ライブラリのゲート: 各リポジトリで cargo test -j 4 --locked --workspace。状態機械の検査。コンセンサスなし、複数検証者なし、プロセス分離なし。

Avalanche L1 のゲート（defmi）: RPCChainVM 45 で Rust VM を起動する AvalancheGo プロセス 5 台。口座を持たない note、事前承認済みの予約、7 者 MPC の zkPI、複数 RFQ の原子的決済、法人単位で共有する上限、再起動復旧、状態 root の合意。外部バイナリ（AvalancheGo、avalanche-network-runner、MP-SPDZ）は承認済みの SHA-256 とともに明示的に供給し、スクリプトは決して取得しない。

OCLOB のリリースゲート: Rust の fmt、clippy、全 crate のテスト、React Flow の型検査とビルド、実物の MP-SPDZ、zkPI、DeFMI の DvP、正規形での読み戻し、リプレイの拒否を、遠隔の Linux コンテナ上で一度に実行する。開発用の Mac ではビルドもテストもしない。

本番を阻むもの

健全性の問題、2026-09-07 に発見し同日修正。 値の部分が 0 であることを示す必要のある 5 か所の検証器が、一般の開封証明を使っていた。登録簿との照合証明、bit 分解の範囲証明とその閾値版の連結（zkPI が運び、閾値 DvP パッケージが検証する範囲証明）、quote proof の「勝者の commitment が公開値に開く」段、rule audit の等値の段である。テストで偽造が 2 件成立した。誤った総額に対する照合証明の受理と、300 への commitment の 8 ビット範囲証明の通過である。同日中に全箇所を値を 0 に固定する開封証明に移し、閾値の組み立てにはどのノードの nonce も値の成分を持たない零関係を加え、rule audit の不等値は 1 への commitment に固定した逆元の積として証明するようにし、偽造は 3 つの crate のコピー（zkpi、defmi、qomm）と耐量子統合ブランチの回帰テストになった。変更前に発行された証明は検証を通らない。テストを含む所見の記録は決済リポジトリにある。暗号技術の使い方を参照。
  1. 単一の当事者では開けない決済権限。 OCLOB の研究用ゲートウェイは参加者の固定長の決済権限を単独で復号する。本番には閾値復号か、MPC ノードによる zkPI の共同生成が必要である。
  2. 暗号上だけでなく現実に独立していること。 k-of-n は算術の性質である。7 つの運営者、7 台のホスト、7 つの鍵保管庫、7 つの障害領域は現実世界の性質であり、どれも整えていない。
  3. 再起動をまたいで永続する状態世代。 キュー、レート制限器、nullifier 台帳を認証付き記憶域に置き、ロールバックでリプレイが再び通らないようにする。
  4. 認証、認可、鍵管理: mTLS、テナント別の認可、外部 KMS/HSM、鍵の交代、バックアップと復旧。
  5. share から証明への受け渡し: 検証者は非公開の計算を再実行しない。これを閉じるには MPC 全体の証明と、まだ存在しないコンセンサス性能計測が必要である。
  6. 法的 finality と登録簿への接続: 振替口座簿、CSD、中央銀行の資金脚、監督当局の開示手続き。

レビュー 2 回、記録あり

各リポジトリはレビュー文書を保持し、検査して健全と判断したものも、受け入れなかったものも含め、すべての所見を残している。レビューが変えたものの例: 既定で off で配備ガイドにも載っていなかった束縛の切替 2 つ。3 回引用されながらどこでも計測されていなかった probe の予算。履歴とともに大きくなる状態 root。命名規約の中にしか存在しなかった連結不能性。commit する前にノードが係数を読めた入力検査。呼び出し側が自分の封筒を押し込めた審査証明の名簿。いまも未解明として載っている 1 件の失敗。仕組みを読む前にこれらを読むのは、妥当な順番である。
