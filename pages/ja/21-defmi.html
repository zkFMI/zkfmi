DeFMI: 取引を一度も読まない決済層

分散型金融市場基盤（decentralized financial market infrastructure）。この術語は意図的に借りている。FMI とは CPMI-IOSCO 原則が対象とするもの、すなわち資金決済システム、証券決済システム、清算機関である。ここでの主張は、これがその一つであり、単一の運営者に依らず、決済する内容を読めない、ということである。株式専用の台帳ではない。チェーンに依存しない状態機械が、現金、証券、ファンド、商品、炭素クレジット、その他の制度の下で管理される資産を登録する。

出典: defmi/DEFMI.md（計測 JSON から生成。手で書いた数値はない）· 特記なければ host-c、rustc 1.97.1、群は ed25519。較正値: スカラー乗算 38.4 ± 4.1 µs、40 ビット範囲証明 20.88 ms。

保証するもの、しないもの

DeFMI が検査できるのは、何も開かずに算術だけで決着がつくことに限られる。

保証成り立たせるもの
価値が生成も消滅もしていない残高の commitment の積が発行時の積に等しい（準同型性のみ）
残高が負にならない差分に対する範囲証明
両脚が一緒に動くどちらかを適用する前に両方を検査する
一つの指図は一度だけ決済されるnullifier の登録
資金脚 = 数量 × 価格三つの commitment にわたる積の証明
証券脚は指図どおりの数量である生成元をまたぐ等価証明

DeFMI が検査しないのは、価格が妥当だったか、それが正しい銘柄だったか、である。それらの意味は計算ノードの定足数から来て、指図の署名に載って運ばれる。決済層にそれを再導出させるなら、決済層に平文を渡すことになる。

コストは残高の幅で決まり、それ以外には依らない

線形バックエンドの証明は台帳の残高範囲をビット分解したものなので、幅に対して線形になるはずである。実際にそうなった。構築が 0.98 ms/bit、決済が 0.80 ms/bit、wire 上が 896 B/bit。決済側の切片 2.1 ms は zkPI 指図そのものの検証である。40 ビットでは決済に 34.0 ms かかり、そのうち約 6% が指図で、残りは台帳側の範囲証明である。

ここから導かれるのは、暗号ではなく銘柄登録時の判断である。決済を速くしたいなら、残高の幅を見直せばよい。証券の数量と現金の金額は桁が何段も違うので、レールごとに別の幅を与える。証券を 24 ビット、現金を 48 ビットにすると、両方 48 ビットの場合より 24% 速く決済でき、送るバイト数は 10,752 B 減る。暗号には何の変更もない。

どの銘柄かを、決済層からも隠す

MPC は依頼がどの資産のものかを隠す。決済の段で取引を銘柄ごとのレールに載せれば、それが元に戻ってしまう。一方、全銘柄を一本のレールに載せると、価値の保存は銘柄をまたいでしか成り立たず、資産 A を資産 B として持ち出せてしまう。

そこで使う構成が asset tag である。資産 a を q 単位持つとは A_a^q · h^r を持つことであり、移転ごとに新しい y で H = A_a · h^y を公開し、すべての範囲証明は H に対して作る。この偽装を実在の資産に束縛するのは差分に対する範囲証明である。支払側の残高はすでに A_a の下にあるので、他の tag ではそれを開けない。決済一件あたりの追加は 32 B と生成元をまたぐシグマ証明一つで、時間の増分は計測の 0.2 ms のノイズの中に収まる。one-of-many 所属証明（Groth–Kohlweiss）は残高を口座に発行するときに一度だけ必要で、検証は 4 銘柄で 0.58 ms、64 銘柄で 2.24 ms。

計測した攻撃の系統: 別の資産として登録済みの tag で残高を持ち出す、登録されたことのない点を使う、のどちらも "remainder does not equal balance minus amount" で拒否される。パッケージは 64 銘柄のどれであってもバイト単位で同一である。

ネッティング: gross-gross、gross-net、net-net

これらは BIS の DvP モデル 1、2、3 であり、同時に、範囲証明が何本どこに落ちるかの問題でもある。gross のレールは注文ごとに取引後のポジションが非負であることを証明するので、構成上、決済不履行は起こり得ない。その代償が順序依存である。net のレールは期間中は準同型に累積するだけで何も証明せず、締めの時点で参加者ごとに一度、net 額の充足を示す。commitment は大きさだけでなく符号も隠すので、途中で負になったポジションからは何も漏れない。

commitment としての日中当座貸越

実務では、net のポジションを負にする注文をすべて拒否するわけではない。差し入れた担保に対して限度を与える。これはまさに日本銀行の日中当座貸越である。ここでは限度が commitment であり、充足は position + limit について証明するので、証明はポジションがゼロのどちら側にあったかを決して語らない。限度のコストは実質ゼロである。なしで 9.4 ms、ありで 9.2 ms、同じ幅の範囲証明を別の commitment に対して作るだけである。限度の付与は構築 9.4 ms、検証 1.3 ms で、一度きりである。

受付、担保差入、当座貸越、支払は一つの事象であるべきだが、現在のコードでは一つの事象になっていない。PositionBook::grant と Cycle::admit は別々の呼び出しで、差し入れた担保をロックする状態もない。限度のコストは計測済みだが、原子性は文書に書かれた要件であって、実装されていない。

デフォルト・ウォーターフォール

net のレールは締めの時点で不履行になり得る。その不履行をどの順序で処理するかがこの取り決めの本体なので、順序を強制する。トランシェ k はトランシェ k−1 が尽きた後にしか引き出せない、という条件を draw_k × remaining_{k−1} = 0 と書き、その積の commitment を単位元に固定する。コストはトランシェあたり構築 11.2 ms、検証約 1.4 ms の線形で、デフォルトごとに一度である。

清算機関を間に入れる

更改の下では、検証すべき二者間の分割は残らない。A と B の取引は、A 対清算機関と清算機関対 B になる。債務は commitment なので、一本の辺を二本に置き換えるのは乗算二回で、証明は要らない。清算機関の帳簿は同じ構成によってフラット（差引ゼロ）になる。参加者 8 で計測すると、net-net は取引数とともに増える（16 件で 66 ms、256 件で 794 ms）が、清算済みサイクルは増えない（19 ms から 38 ms）。更改のコストは取引あたり 0.53 µs。これで得られるのは、attestation 系統が守れる形になることである。名前の分かる清算機関が反対側に立ち、その帳簿がフラットであることは誰でも検査でき、その証拠金は commitment された上限であり、その資本は CPMI-IOSCO と EMIR が置くとおりウォーターフォールの中にある。

やらないことが四つある。債務グラフは資産ごとなので、銘柄をまたぐ更改は拒否する。異なる提供者にあるポジションを一括の証拠金で相殺することはしない。算術上の妥当性は法的な妥当性について何も言わない。そして清算機関は取引を落とすことはできる。ただし取引をでっち上げることはもうできない。check_novation が、更改前グラフのすべての辺に両当事者の署名を要求するからである。

誰が誰に払ったかを隠す: note 台帳

asset tag は何をを隠す。口座型の台帳では、決済ごとに四つの handle が平文で名指しされたままで、繰り返し現れる handle は取引相手のグラフを描いてしまう。そこで口座を note に置き換えた。note は C = g^S · A_a^v · h^r で、S を構成できるのは受取人だけである。使用時は S を隠したまま、ring のうち一つがこの S を持つことを Groth–Kohlweiss で示す。

この非対称性こそが狙いである。wire は倍にするごとに 224 B 増え、検証は ring 512 まで 10 ms を下回る。増えるのは証明で、それは支払側自身の機器で行う。つまり匿名集合の上限を決めるのは支払側であって、決済ノードではない。受取人は note あたり 0.063 ms、スカラー乗算一回でプールを走査し、プールに比例するコストはこれだけである。同じアドレスへの二つの支払は連結できない。

履歴とともに増えなくなった状態ルート

ring のベンチマークで、検証がプールとともに増えていくのが見つかった。check_spend の中にプールに比例するものはない。あったのは状態ルートで、保持したことのあるすべての note を再圧縮し、使用済みのすべての serial を再整列することを、決済一件につき四回行っていた。4,096 note では、暗号 8 ms の横で 61.3 ms の帳簿付けをしていたことになる。note は追記のみ、serial は挿入のみなので、ルートは今では変更ごとに一度延長する走行ハッシュになった。0.15 µs で一定、全走査の 15.3 ms に対して。

二つの台帳をまたぐ PvP

状態を共有しない二つの台帳には両脚を動かす関数がなく、第三者なしの公正な交換は一般には不可能なので、何かが両者の間を渡らなければならない。ハッシュロックでは前像を渡すが、それは両方の台帳に平文で残るので、両方を読める者は両脚を結び付けられる。代わりに使うのが adaptor signature である。先手側が一方の台帳で claim すると後手側にスカラーが渡り、各台帳に記録されるのは、相手の台帳と何も共通点のないふつうの署名である。

1. Bob   -> Alice : Y = g^y
2. Alice           prepares leg A; her money leaves her account
   Alice -> Bob   : a pre-signature over "leg A", adapted to Y
3. Bob             prepares leg B, and sends his own pre-signature
4. Bob             claims on A  -> he is paid, and y becomes readable
5. Alice           reads A, recovers y, claims on B  -> she is paid

Bob が秘密を引いて先に動くので、Bob は決してリスクに晒されない。Alice が晒されるのは手順 4 と 5 の間のちょうど一つの窓で、二つの期限の隙間が彼女の反応時間を覆っているとき、かつそのときに限り安全である。この隙間が、この取り決めのヘルシュタット・リスクである。32 ビットのレールで計測すると、脚の準備 1.29 ms、先手側の claim 0.05 ms、後手側の反応 0.06 ms、期限切れの脚の巻き戻し 0.55 µs。資金をリスクに晒すのは暗号ではない。期限の隙間は二つの台帳の決済 finality が決め、それは 3 桁から 5 桁大きい。窓を短くしたい配備は、速い証明ではなく finality を選んで調達すべきである。

一つのチェーン上なら、二つの DeFMI 市場を一つのトランザクションから呼ぶこともできる。追加コストなしで原子的、露出ゼロ、そしてそのトランザクション自体が結び付きになる。adaptor 系統は呼び出しが 4 倍、検証が 3.0% 増え、その代わりに連結不能性が得られるが、それも handle を市場ごとに導出しているときに限る。zkPI のページの表は、一つの名前をどこでも使うと観察者が 1.000、市場ごとの handle なら 1/k になることを、暗号は変えずに示している。

正本台帳と一致させる

日本の振替制度の下では、この台帳は振替口座簿にはなれない。権利は振替機関と口座管理機関が保持する記録に依る。したがって DeFMI は鏡であり、照合はその取り決めの代価である。それは一行の代数である。commitment は乗算できるので残高の積はその和への commitment になり、asset tag の下で正本台帳の数字を割り出せば、残るものは h の純粋な冪でなければならない。その指数を知っていることを証明すれば、合計が一致することが証明され、それ以外は何も語らない。証明は台帳の中身が何であれ 96 B で、4,096 ポジションの検査は 0.65 ms。3-of-7 の定足数は同じ命題を合計の blinding のシェアから 4.5 ms で組み立てるので、誰も合計を持たない。合計を持つ者は台帳全体を開けてしまうので、これは重要である。

不一致は合否でしか出ない。どこが違うかを見つけるには小計が要り、主張した小計はすべて公開になって、一ポジション、つまり一つの残高まで降りていく。これは DeFMI の中で唯一、意図的に開示する操作であり、何かがおかしい日にこそ手が伸びる操作でもある。ポジションごとに数字を持つ正本台帳なら、追加コストなしに場所を特定できる。

監査人に一切れだけ見せる

note のウォレットは閲覧鍵（view key）と支出鍵（spend key）からなる。scope の区切りは鍵の中ではなく、アドレスの中にある。scope（銘柄、四半期、mandate）はウォレットの seed からハッシュで自身のアドレスを導出し、そこへ送られた note はその scope の閲覧鍵で見つかり、他の何によっても見つからない。付与は発行 0.08 ms、検査 0.07 ms。scope を持つ者はプールのうち付与された 5 分の 1 にちょうど届き、serial は一つも復元できない。serial には支出鍵が要るからである。

消えない限界が三つある。付与は取り消せないので、失効とは次の scope へ移ることであり、それはアドレス管理の行為である。Rolling はその予定表を、規律ではなく対象物にする。閲覧鍵は入金側だけで、出金は別の開示になる。そして scope の細かさは支払側の協力の範囲にとどまる。前四半期のアドレスを使う支払側は note を前四半期の scope に入れてしまい、arrived_off_schedule がそれを検知するが、防ぐものはない。

handle を持てるのは誰か

handle は誰でも選べる。許可が要るのは審査を通ることで、審査名簿が保持するのは handle ではなく封印された封筒 C = a·G + r·h なので、一つ追加しても一様ランダムな点が現れるだけで、加入のタイミングはどの項目がその人のものかを何も語らない。所属は固定した群に対する one-of-many で証明する。証明ごとに新しい ring を作ればより秘匿されるように見えるが実際は逆で、重なった ring は交わるからである。Schnorr 証明が handle を封筒が定める一つに固定するので、一つの審査から出るのは一つの handle であり、一族ではない。Roll::vetted() と Roll::crowd() は公開で、匿名集合の大きさは誰でも検査できる。審査の事象を隠すことと群の大きさを証明することは同じ情報であり、設計は後者を選ぶ。

{{chart:vetting}}

検証は群とともに倍になると予測したが、実際は約 1.4× にとどまり、まとめて行うマルチスカラー乗算の効果が現れた。群 128 で検査は 3.84 ms、証明は 1,676 B なので、128 を既定値とする（vetting::CROWD）。数千の群には回路の中の Merkle 木が要り、ここにあるシグマ・プロトコルや Bulletproofs とは別の証明系になる。

Avalanche L1

配備済みの実行経路は avalanche/defmivm/ にある専用の非 EVM カスタム VM で、AvalancheGo が RPCChainVM プロトコル 45 で起動する。ネイティブの状態遷移: 資産登録、口座開設、事前承認済みの予約、原子的な複数脚の決済。完全な受入ゲートは、口座を持たない note、事前承認済みの予約、7 者 MPC の zkPI、複数 RFQ の原子的決済、法人単位で共有する上限、再起動復旧、状態ルートの一致を覆う。

まだ欠けているもの

  • 検証者は提出された証明一式を完全に検証するが、非公開の MP-SPDZ トランスクリプトを再実行することも、シェアから証明への受け渡しを証明することもしない。この委員会への信頼を取り除くには、非公開の計算全体の証明と、別途の合意ベンチマークが要る。
  • 受付、担保差入、限度、支払は一つの原子的な事象になっていない。
  • note を送った者は、それが使われたことが分かる。この構成では避けられない。
  • 第二の決済通貨を追加するのは口座開設の判断であり、コード変更ではない。tag 付きの資金脚は、口座の建値通貨に対して開くからである。
