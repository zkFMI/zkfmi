市場以外の業務システム

QOMM は指図の発行元の一つ、すなわち価格を決めて指図を発行する市場である。誰が何を、どの条件で動かしてよいかを決める他の業務システムも、その判断を zkPI に載せ、入力を読まない DeFMI に決済させることができる。秘匿の見積も、MPC による値付けも、メイカーとテイカーも要らない。

出典: defmi/doc/ja/DEFMI_ZKPI_USE_CASES.md（2026-08-30 時点の調査）

形が合うとき

次の三つの条件がそろう業務が向いている。

  1. 決済の前に、資格、限度、担保、契約条件のいずれかを確認しなければならない。
  2. その確認に使う個人情報、保有、金額、内部の判断を、決済参加者全員に見せてはならない。
  3. 条件が満たされたら、どちらの脚も単独では実行されず、どの指図も二度は使われない。

実現しやすい順

#用途誰が zkPI を発行するか最も近い先行例検証すべき差
1ファンドの申込、解約、キャピタル・コールトランスファー・エージェント、ファンド管理者、KYC 提供者が共同で。資格が有効、金額が規則と投資家ごとの上限の内、資金が予約済み、口数が発行可能、基準価額の時点が確定Project Guardian（MAS）が DLT 上で申込と支払を自動化している資格、個別の上限、金額を決済参加者から隠す。別のファンドシステムからの一回限りの指図を、運営者のいない台帳が決済する
2担保と証拠金: 差入、差替、返還承認済みの資格・ヘアカット・集中度の回路を持つ担保エンジン。ポートフォリオを見せずに要件を満たしていることを証明するトライパーティ担保、CCP の証拠金請求秘密のポートフォリオに対する充足の証明。同時に来る請求の順序付けと、正本状態の中での法人単位の上限
3銀行間および越境 PvP二つの発行者と二つの資金予約を一つの指図に束縛する。制裁と権限の審査は証明として載せるFnality、Partior、mBridge、Project Agorá台帳ごとに無関係な署名を用いる adaptor signature による PvP。露出窓は証明ではなく finality が決める
4発行、償還、利払、配当発行者と支払代理人デジタル債券プログラム（SDX、eWpG の登録簿）保有者の集合と金額を隠す。コーポレート・アクションをまたいだ保存則
5不動産と高額資産の移転登録機関とエスクロー業者権原トークン化の実証登録簿が外部にあり、DeFMI がそれを鏡として写す DvP
6政府・国際機関の約束手形、拠出金、補助金国庫と支出機関—資格を隠した条件付き支出
7債権とインボイス金融Aethel 型の債権システムサプライチェーン金融のプラットフォームAethel のページを参照
8環境・コモディティ証書: 発行と償却登録簿の運営者炭素登録簿償却を一回限りの nullifier として扱う。保有者を隠す
9保険金請求と給付の支払保険者と査定者パラメトリック保険請求条件を証明し、請求者の情報は出さない

最も実用に近い製品は 1 番目である。二つのものが同時に動くという点で DeFMI の DvP そのままであり、役割も少ない。研究課題として最も強いのは 2 番目、秘密のポートフォリオに対する充足の証明である。長期的に最も大きな事業は 3 番目である。

混同してはならない二つの越境の場合

  • グループ内の PvP/DvP。親会社、子会社、インハウス・バンクは規則と決裁権限の系統を共有するので、一つの参加者モジュールが会計、財務、カストディをつなぎ、承認済みの指図を DeFMI に渡せる。必要なのは暗号化した永続キューで、MPC が停止しても指図が失われないようにする。MPC の代わりに手元で計算しない、証明のない送信をしない、要求 id による冪等な再送、元の順序の保持、期限切れ要求の自動延長をしない、そして復旧後はカバー・スロットを交えた一定間隔の送信に戻し、まとめて送ることでどの要求が本物だったかを告げないようにする。
  • ステーブルコインを資金脚とする独立当事者間。売り手と買い手は何も共有しないので、内部の承認は信頼の根拠にならない。各当事者のモジュールは、自身の KYB と署名権限、自身が事前予約した資産または USDC、ステーブルコインのチェーン、コントラクト、発行者、凍結、finality の条件を取引時点で、そして両脚にまたがる一つの取引 id、金額、期限を束縛する。ステーブルコインの台帳は、独自の障害状態機械（reorg、期限切れ、発行者による凍結）を持つ差し替え可能な資金の経路であり、グループ内決済の設定変更ではない。

すべての指図の発行元が解かねばならない六つの問題

  1. 誰の判断が有効か。どの鍵、どの定足数、どの統治か。
  2. 証明した条件と決済した対象を同じものにすること。
  3. 同時に出た指図が共有の上限を超えないようにすること。
  4. 外部台帳との障害の整合。どの障害が原子性を壊すかを定め、壊れた構成を DvP と呼ばないこと。
  5. 後から確認できるのを正しい相手に限ること。紛争、監査、監督のための scope 付き開示。
  6. finality の法的な時点を定めること。

主張してよいこと

DLT 上の DvP、トークン化預金と証券、支払前のコンプライアンス審査、ZK によるコンプライアンス証明、担保や申込の自動化は、それぞれ単独では新しくない。検証すべきは組み合わせである。異なる指図の発行元が一つの型の指図を発行することによる、業務上の判断と決済の分離。元データを再構成しない決済。指図をまたいで再利用できない一回限りの権利。資金、預金、証券、口数、担保、証書を一つの指図の境界の下に置くこと。分散運用でも発行者・登録機関・清算の権限を証明の中に保つこと。事後の選択的な検証。「世界初」は主張しない。主張があるとすれば、機能ごとの比較を終えた後の、統合された構成とその安全性の定義である。

実装の順序

  1. ファンドの申込と解約。発行者、管理者、投資家、KYC の鍵を分ける。資格、申込上限、資金予約、発行可能口数を zkPI に束縛し、資金の note と口数の note を同時に更新する。同時の申込超過、期限切れ、再送、片脚の失敗を試験する。
  2. 担保と証拠金。適格担保、ヘアカット、集中度限度を承認済みの回路にする。ポートフォリオを見せずに充足を証明する。追加差入、差替、返還。複数の請求の順序付けと法人単位の上限。
  3. 二通貨 PvP。二つの発行者と二つの予約を一つの zkPI に。発行者の停止、期限切れ、再起動、再送の試験。ISO 20022 への対応付けは外部アダプタに置き、DeFMI の型を特定の銀行のメッセージに固定しない。
  4. 外部台帳との接続。模擬のファンド・担保・銀行台帳を独立プロセスとして立てる。署名付きの予約と確認済みの受領証。どの障害が原子性を壊すかの明示的な一覧。

今あるもの: 型付き zkPI、署名と証明の検証、一回限りの識別子、口座名を公開しない note 台帳、同一台帳内の DvP と PvP、発行者権限、事前予約、照合。いずれも QOMM 以外の業務システムから呼び出せる。ないもの: 実際のファンド管理者、CCP、銀行、CSD、登録機関との接続。外部 KYC。物理 HSM。7 拠点での運用。法的 finality。第三者監査。
